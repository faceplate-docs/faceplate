# Руководство по настройке Historian-сервера

## 1. Введение

Данный документ содержит техническое описание настройки и эксплуатации Historian-сервера в составе SCADA-системы Faceplate Studio. Документ предназначен для системных администраторов и инженеров автоматизации.

## 2. Архитектура системы хранения данных

### 2.1. Типы серверов

В SCADA-системе Faceplate Studio реализовано два основных типа серверов для хранения исторических данных:

- **Runtime-сервер** — основной компонент системы, обеспечивающий обработку данных в реальном времени и их передачу другим компонентам системы.
- **Historian-сервер** — специализированный сервер для долговременного хранения архивных данных. Использование Historian-сервера позволяет разгрузить Runtime-сервер и применить оптимальные аппаратные решения для задач хранения и анализа исторических данных.

### 2.2. Преимущества распределенной архитектуры

**Надежность и отказоустойчивость:** использование нескольких серверов повышает отказоустойчивость системы за счет распределения функциональной нагрузки и обеспечения резервирования данных.

### 2.3. Схемы хранения данных

Система поддерживает следующие конфигурации:

1. **Runtime-сервер** — хранение данных на основном сервере обработки.
2. **Runtime-сервер + Historian-сервер** — распределенное хранение с выделенным сервером для архивных данных.

Для выбора оптимальной схемы хранения необходимо настроить параметры архивирования, которые описаны в следующем разделе.

## 3. Конфигурация базы данных

База данных в Faceplate Studio организована в виде трех основных разделов: Runtime, Log и Timeseries. Каждый раздел отвечает за хранение определенного типа данных.

### 3.1. Раздел Runtime

Раздел Runtime предназначен для конфигурирования параметров получения и хранения данных, поступающих в реальном времени.

![Конфигурация раздела Runtime](/Historian/images/img_1.png)

*Рисунок 1 — Конфигурация раздела Runtime в интерфейсе базы данных*

На рисунке показана конфигурация параметров хранения данных для сервера `fp@main-rt-server2.fp`. Система поддерживает следующие режимы хранения:

- **`:atom:disc:`** — хранение на жестком диске с использованием модуля **`:atom:zaya_rocksdb`**.
- **`:atom:ram:`** — хранение в оперативной памяти с использованием модуля **`:atom:zaya_ets`**.
- **`:atom:ramdisc:`** — комбинированное хранение (RAM + диск) через модуль **`:atom:zaya_ets_rocksdb`**.

### 3.2. Раздел Log

Раздел Log предназначен для конфигурирования параметров получения, хранения и управления сообщениями системы (алармами, событиями).

![Конфигурация раздела Log](/Historian/images/img_2.png)

*Рисунок 2 — Конфигурация раздела Log для хранения алармов*

Конфигурация задает параметры хранения для сервера `fp@main-his-server1.fp`. Основные параметры:

- **`:atom:dir:`** — путь к директории для хранения данных алармов.
- **`:atom:disc:`** — использование модуля **`:atom:zaya_rocksdb`** для хранения на диске без дополнительных параметров.
- **`:atom:max_age:`** — период хранения алармов в днях. По истечении указанного срока база данных соответствующего временного диапазона удаляется вместе со всеми содержащимися в ней алармами.
- **`:atom:read_only_age:`** — возраст данных в днях, при достижении которого соответствующая база данных (шард) переводится в режим read-only. В этом режиме запись и модификация запрещены, межузловая синхронизация для данного шарда отключается.
- **`:atom:shard_depth:`** — временной диапазон в днях, который покрывает один шард базы данных. Все алармы, созданные в пределах этого диапазона, закрепляются за соответствующим шардом.

### 3.3. Раздел Timeseries

Раздел Timeseries предназначен для конфигурирования параметров получения, хранения и управления архивными данными временных рядов.

![Конфигурация раздела Timeseries](/Historian/images/img_3.png)

*Рисунок 3 — Конфигурация раздела Timeseries с настройками RocksDB*

Данная конфигурация определяет параметры хранилища архивов на основе RocksDB. Основные параметры:

- **`:atom:buffer_limit:`** — ограничение размера буфера (1 ГБ).
- **`:atom:nodes:`** — указание узла хранения с директорией для размещения данных.
- **`:atom:remove_age:`** — глубина хранения данных. Данные старше указанного периода (например, 365 дней) автоматически удаляются.
- **`:atom:open_options:`** — настройки открытия и работы базы данных RocksDB:
  - Размер блока: 32 КБ;
  - Сжатие: lz4;
  - Триггеры компактации на уровне 0;
  - Ограничения: размер уровня — 1 ГБ, количество файлов — 512, фоновых задач — 16;
  - Буферы записи: 128 МБ, максимум 4 буфера.
- **`:atom:read:`** — чтение с кешированием, без проверки контрольных сумм.
- **`:atom:write:`** — асинхронная запись данных.
- **`:atom:shard_depth:`** — глубина шардирования данных по дням.

Данная конфигурация оптимизирована для обеспечения высокой производительности и долговременного хранения архивных данных.

## 4. Процедура присоединения Historian-сервера

Присоединение Historian-сервера к системе необходимо для организации хранения данных типа Timeseries (архивы) и Log (сообщения). Процедура выполняется в следующей последовательности:

### 4.1. Запуск Historian-сервера

Запустите Historian-сервер с указанием Runtime-сервера, к которому он будет присоединен. Используйте следующую команду:

```
env ATTACH_TO=fp@rt-server2.fp ./bin/fp_historian console
```

где:

- **ATTACH_TO=fp@rt-server2.fp** — переменная окружения, указывающая имя Runtime-сервера, к которому присоединяется запускаемый Historian-сервер;
- **./bin/fp_historian** — исполняемый файл для запуска Historian-сервера;
- **console** — режим запуска сервера (консольный режим с выводом логов в терминал).

### 4.2. Конфигурация базы данных

Добавьте Historian-сервер в конфигурацию базы данных, выполнив следующие действия:

1. Откройте объект базы данных в интерфейсе конфигурации системы.
2. Внесите изменения в разделы Log и Timeseries, указав Historian-сервер в качестве узла для хранения данных.
3. Укажите путь для хранения данных Log и Timeseries на Historian-сервере.
4. Скомпилируйте и сохраните файл конфигурации.

### 4.3. Проверка корректности настройки

Проверьте логи серверов Faceplate и Historian на предмет отсутствия ошибок. Это необходимо для подтверждения корректности подключения и настройки Historian-сервера.

### 4.4. Удаление Runtime-сервера из конфигурации хранения

После успешного переноса данных и проверки работоспособности удалите Runtime-сервер из списка узлов хранения в объекте базы данных. Это обеспечит сохранение всех архивных данных исключительно на Historian-сервере.

### 4.5. Финальная проверка

Проведите повторную проверку логов системы для подтверждения корректности функционирования и отсутствия ошибок после перенастройки хранения данных.
