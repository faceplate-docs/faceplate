# 1\. Обзор модуля

## 1.1. Назначение модуля

Модуль Git - встроенный инструмент для версионного контроля проектов Faceplate позволяет сохранять историю изменений, организовывать совместную работу нескольких инженеров через синхронизацию прикладного проекта с внешним сервером GitLab.

## 1.2. Архитектура

Работа с версиями в Faceplate строится на взаимодействии трех независимых уровней. Это позволяет инженеру сохранять промежуточные результаты локально даже при отсутствии связи с внешним сервером GitLab.

**Схема потока данных:**

**Локальный проект** ↔ **Локальный Git-репозиторий** ↔ **Удаленный сервер GitLab**

**Описание уровней:**

- **Локальный проект (Рабочая область):**
  - Это то, что вы видите и редактируете в Studio прямо сейчас: текущие мнемосхемы, активные теги и скрипты.
  - Изменения на этом уровне еще не защищены историей версий. Если вы удалите объект здесь, его нельзя будет восстановить.
- **Локальный Git-репозиторий (База версий):**
  - Находится на том же физическом сервере (узле), где установлен Faceplate.
  - Когда вы нажимаете **Commit**, «снимок» проекта перемещается из рабочей области в этот скрытый архив.
  - Это позволяет вам иметь полную историю изменений и возможность отката (**Reset**) локально, без обращения к внешней сети.
- **Удаленный сервер GitLab:**
  - Внешнее централизованное хранилище.
  - Когда вы выполняете **Push**, ваши локальные коммиты отправляются на сервер.
  - Это обеспечивает:
    - **Резервное копирование:** данные защищены от поломки локального сервера.
    - **Командную разработку:** другие инженеры могут забрать ваши правки через **Pull**.

# 2\. Интерфейс и основные понятия

Интерфейс модуля разделен на три вкладки, соответствующие жизненному циклу разработки: Settings, Local Diff и Remote Diff.

- Settings (Настройки): Здесь производится конфигурирование подключения к репозиторию, клонирование (Clone) и инициализация проектов (Init).
- Local Diff (Локальные изменения): Раздел для управления текущими изменениями на сервере. Здесь выполняются команды фиксации (Commit), отправки (Push) данных, внести изменения из одной ветки в другую (Merge request), (Reset).
- Remote Diff (Удаленные изменения): Раздел для взаимодействия с внешним репозиторием. Здесь можно забрать обновления (Pull), откатить версию (Rollback) или выполнить слияние веток (Rebase).

## 2.1. Глоссарий команд Git

- Commit: Фиксация («снимок») текущих локальных изменений с описанием.
- Push: Отправка локальных коммитов на удаленный сервер.
- Pull: Загрузка и применение изменений с удаленного сервера.
- Reset: Отмена незафиксированных правок (возврат к последнему коммиту).
- Rollback: Возврат всего проекта к состоянию одной из прошлых версий.

# 3\. Настройка репозитория (вкладка Settings)

Перед началом работы необходимо определить, как проект будет связан с Git. Доступно два сценария:

## Клонирование (кнопка Clone)

Используется, если проект уже создан в GitLab и его нужно «скачать» на новый сервер Faceplate.

- **Remote URL:** HTTPS-ссылка на ваш репозиторий.
- **Auth:** Логин и Пароль (или Access Token) от GitLab.
- **Branch name:** Ветка (обычно main или master).
- **Project prefix:** Путь к папке проекта внутри репозитория (позволяет хранить несколько проектов в одном репозитории).

## Инициализация (кнопка Init)

Используется для создания нового репозитория «с нуля» или привязки текущего локального проекта к пустому репозиторию в GitLab.

- После заполнения данных нажмите **Init**.

После завершения появится кнопка **Reset**, которая позволяет переинициализировать проект в случае ошибки.

## Подключение нового пользователя

При клонирование проекта с репозитория все локально созданные пользователи будут замещены. Для того, чтобы восстановить доступ к подключенному репозиторию необходимо выполнить ввод имени пользователя и пароля r репозиторию.

# 4\. Управление изменениями

## 4.1. Локальные изменения (Local Diff)

Этот раздел управляет данными на вашем текущем сервере.

- **Просмотр изменений:** Система автоматически подсвечивает измененные файлы (теги, экраны, скрипты).
- **Commit:** Введите краткое описание (например, _"Добавлена мнемосхема насосной"_) и нажмите Commit. Изменения сохраняются в локальную историю.
- **Push:** Нажмите для отправки всех накопленных коммитов в GitLab. Только после этого коллеги смогут их увидеть.

## 4.2. Удаленные изменения (Remote Diff)

Раздел для получения данных и управления историей.

- **Pull:** Нажмите, чтобы обновить свой проект данными, которые загрузили другие разработчики.
- **Rebase:** Позволяет «переписать» ваши локальные изменения поверх последних удаленных правок для сохранения линейной истории.
- **Rollback:** Позволяет выбрать любую точку в прошлом и вернуть проект в то состояние.  
    **Внимание:** Команды Rollback и Reset безвозвратно удаляют текущие незафиксированные изменения. Будьте осторожны!

# 7\. Процедуры

## 7.1. Первичная настройка и развертывание

Предварительные действия:

- Экземпляр Faceplate развернут для клонирования существующего проекта или инициализации нового репозитория.
- Доступна учетная запись администратора по умолчанию: **system** с паролем установленным по умолчанию: 111111.

**Важно!**

Все пользовательские настройки при клонировании будут удалены.

Для первого входа и после клонирования можно использовать пароль по умолчанию.

- **Проверить Project Prefix:** Если в одном репозитории хранится несколько объектов (например, «Цех 1» и «Цех 2»), убедитесь, что указан верный путь к папке. Иначе вы скачаете (Pull) или зальете (Push) файлы не туда.
- **Валидация Token/Password:** Если используется Access Token вместо пароля, убедитесь, что у него не истек срок действия и стоят права read_repository и write_repository.
- **Выбор ветки:** Проверьте, что в поле Branch name указана ваша рабочая ветка (например, dev), а не основная main, если в компании принята политика разделения веток.

Клонирование проекта из репозитория:

- Войти в студию по учетной записью **system** - администратор по умолчанию
- Перейти в раздел Пользователи и создать нового пользователя, дать ему права администратора и задать лимит ограничения по используемой памяти.
- Переключиться на вновь созданного пользователя.
- Перейти в раздел Git, ввести необходимые данные, нажать кнопку Clone и дождаться завершения загрузки.
- Созданный пользователь будет замещен загруженными из репозитория учетными записями пользователей.
- Выбрать существующего пользователя с правами администратора либо создать нового, задать пароль и переключиться на него.
- Перейти в раздел Git ввести заново пароль к репозиторию, после успешной аутентификации пользователь получит права на работу с Git.

## 7.2. Подготовка и публикация изменений (Git Workflow)

Шаг 1. Перед началом работы (Синхронизация)

- **Выполнить Pull:** Перейдите во вкладку Remote Diff и нажмите **Pull (Выгрузить)**. Это гарантирует, что вы работаете с актуальной версией проекта и не перезапишете чужие правки.
- **Проверить Studio:** Убедитесь, что после загрузки обновлений все объекты (теги, экраны) отображаются корректно.

Шаг 2. Разработка и проверка

- **Локальная проверка:** Перед фиксацией изменений проверьте работоспособность созданных объектов в Studio.
  - _Пример:_ Если вы создали архив (как в практическом примере), убедитесь, что тег к нему привязан.
- **Отсеивание лишнего:** Загляните во вкладку Local Diff. В списке изменений должны быть только те файлы, которые вы действительно правили.
  - _Если вы случайно изменили лишнее, используйте_ **_Reset_**_, чтобы откатить эти файлы до исходного состояния._

Шаг 3. Фиксация (Commit)

- **Информативное сообщение:** Напишите короткий, но понятный комментарий.
  - _Плохо:_ "1", "fix", "update".
  - _Хорошо:_ "Добавлен архив archive_pressure", "Изменен цвет кнопок на главной мнемосхеме".
- **Нажать Commit:** Теперь изменения сохранены в локальной истории вашего сервера.

Шаг 4. Публикация (Push)

- **Нажать Push:** Отправьте зафиксированные данные в GitLab.
- **Проверка в GitLab:** (Рекомендуется) Откройте веб-интерфейс GitLab и убедитесь, что ваш коммит появился в списке и ветка обновлена.

## 7.3. «Чистая» разработка (Local Diff)

Помогает избежать ситуации «у меня всё работает, а после пуша проект у всех сломался».

- **Просмотр списка изменений:** Перед нажатием **Commit** пролистайте список файлов. Нет ли там случайно удаленных скриптов или тегов?
- **Разделение задач:** Если вы сделали две разные задачи (например, настроили алармы и изменили цвет кнопок), сделайте **два разных коммита**. Это позволит в будущем откатить только алармы, не теряя правки по графике.
- **Использование Reset до коммита:** Если в процессе тестов вы изменили системные параметры «для себя» (например, уменьшили периоды опроса), не забудьте нажать **Reset** для этих файлов перед финальным коммитом.

## 7.4. Конфликты и совместная работа (Remote Diff)

Когда два инженера одновременно правили один и тот же экран.

- **Rebase вместо простого Merge:** Если система сообщает о конфликте, используйте **Rebase**. Это «переставит» ваши коммиты в конец очереди после правок коллеги, сохранив историю проекта линейной и понятной.
- **Проверка после Rebase:** После слияния веток обязательно зайдите в Studio и убедитесь, что ваши объекты и объекты коллеги «подружились» (например, ваши кнопки по-прежнему привязаны к его новым тегам).
- **Rollback как крайняя мера:** Если после Pull проект перестал запускаться, используйте **Rollback** не на самый последний, а на предпоследний стабильный коммит (ищите в истории описание, в котором вы уверены).

## 7.5. Работа с историческими данными и архивами

Особенности Faceplate, связанные с Git.

- **Синхронизация структуры архивов:** Помните, что Git переносит _структуру_ архива (названия полей, типы данных), но не сами данные (исторические тренды).
- **Проверка связей:** Если вы получили (Pull) новый архив от коллеги, проверьте, что на вашем узле Faceplate создана соответствующая база данных или папка для хранения истории.

## 7.6. Завершение смены / Передача проекта

- **Пустой Local Diff:** Перед уходом убедитесь, что вкладка Local Diff пуста (все изменения либо закоммичены, либо сброшены через Reset).
- **Final Push:** Проверьте, что счетчик исходящих коммитов равен нулю. Если данные остались только в локальном репозитории, другой инженер их не увидит.
- **Комментарий-статус:** Последний коммит дня должен быть максимально подробным (например: _"Экран котла №1 готов на 80%, не привязаны алармы давления"_).

## 7.7. Практический кейс: Коллективная разработка

Рассмотрим сценарий работы двух инженеров над одним проектом:

### **Этап 1: Создание базы (Инженер №1)**

- Создает архив archive_pressure и привязывает к нему тег.
- Переходит в **Local Diff**, пишет сообщение _"Added pressure archive"_ и нажимает **Commit**, затем **Push**.
- Теперь изменения находятся в безопасности на сервере GitLab.

### **Этап 2: Добавление графики (Инженер №2)**

- Выполняет **Pull** во вкладке **Remote Diff**. У него в проекте мгновенно появляется архив, созданный первым инженером.
- Создает мнемосхему, добавляет объект _Input-Output field_ и привязывает его к archive_pressure.
- Делает **Commit** (_"Added main screen"_) и **Push**.

### **Этап 3: Финализация**

Инженер №1 делает **Pull**, получает готовую мнемосхему и проверяет работу всей системы в Runtime.
