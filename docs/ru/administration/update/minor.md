# Глоссарий

| Термин | Значение |
|---|---|
| Узел | Один запущенный сервер FACEPLATE. Имя узла имеет вид `fp@<сервер>`, см. [«Узлы кластера»](../nodes/nodes.md) |
| Кластер | Узлы, которые работают вместе с одним проектом и одной базой |
| Каталог установки | Папка на сервере, в которую установлен FACEPLATE. В ней лежат папки `bin`, `erts-<версия>`, `etc`, `lib` и `releases`. После первого запуска в ней появляются папка `logs` и база `DB`, после запуска в фоне — папка `log`, а после подключения модуля Git к репозиторию — папка `cvs` |

# Введение

При минорном обновлении и патче новая версия запускается на базе прежней и сама переводит её на свой формат. Проект, архивы и журнал событий остаются в базе и переходят в новую версию, переносить их не нужно.

Узлы кластера обновляют по одному. Пока обновляется узел, остальные работают, поэтому Runtime не останавливается. Узел новой версии присоединяется к узлам прежней версии и работает с ними вместе, пока не обновлены все узлы. Если узел один, Runtime на время обновления останавливается.

Понадобятся доступ к файлам серверов (например, по SSH) и Studio.

# Основная часть

## Как идёт обновление

1. Один узел останавливают, остальные продолжают работать.
2. На сервере этого узла копируют каталог установки в резервную папку, а новую версию распаковывают поверх самого каталога установки. База остаётся на месте.
3. Узел запускают как обычно. Первый обновлённый узел переводит базу кластера на новую версию, узлы прежней версии продолжают работать с ней.
4. Убедившись, что узел работает, так же обновляют следующий.

В примере кластер из узлов `fp@server1.fp` и `fp@server2.fp`. Команды выполняются из папки, в которой лежит каталог установки `faceplate`.

## Порядок обновления

Шаги 1–3 выполняют один раз, шаги 4–10 — для первого узла, шаг 11 — для каждого следующего.

### 1. Ознакомиться

Прочитайте описание выпуска новой версии.

### 2. Подключиться

Проверьте, что все узлы работают: Studio, панель **Сервера**, см. [«Узлы кластера»](../nodes/nodes.md).

Подключитесь к серверу узла, который обновляете.

### 3. Экспортировать

Сохраните файл экспорта проекта, см. [«Импорт и экспорт проекта», раздел «Экспорт»](../../project_objects/import_export/import_export.md#экспорт). Это запасная копия объектов проекта. Она понадобится, если при неудачном обновлении не удастся вернуть резервную копию каталога установки, которую делают в шаге [5](#5-сохранить).

### 4. Остановить

Остановите узел, см. [«Запуск и остановка узла», раздел «Остановка»](../start_stop/start_stop.md#остановка). Остальные узлы продолжают работать, Runtime работает на них.

### 5. Сохранить

Сделайте резервную копию каталога установки вместе с базой `DB` и журналами `logs`, например в папку `faceplate_backup`. Каталог установки копируют, а не перемещают: в шаге [7](#7-копировать) новую версию распаковывают поверх самого каталога установки, а копия в `faceplate_backup` остаётся без изменений.

### 6. Проверить

Проверьте, что в `/etc/hosts` сервера есть все узлы кластера, см. [«Хранилища», раздел «Подготовка серверов»](../../data_storage/storage/storage.md#подготовка-серверов).

### 7. Копировать

Скопируйте дистрибутив новой версии на сервер и распакуйте его поверх каталога установки.

В дистрибутиве нет папок `DB`, `logs` и `cvs`, поэтому распаковка их не затрагивает: база, журналы и подключение модуля Git в каталоге установки сохраняются. Переносить их из `faceplate_backup` не нужно. Если распаковать дистрибутив в пустую папку, узел запустится с пустой базой и создаст новый проект.

### 8. Изменить

Распаковка кладёт файл `faceplate/releases/<версия>/vm.args` новой версии со значениями по умолчанию. Перенесите в него значения из прежнего файла, он сохранён в `faceplate_backup/releases/<прежняя версия>/vm.args`:

| Параметр | Значение |
|---|---|
| `-name` | Прежнее имя узла, например `fp@server1.fp` |
| `-setcookie` | Прежний cookie, одинаковый у всех узлов кластера |
| `+MIscs` | Прежнее значение |

Описание параметров — в [«Резервировании», раздел «Настройка виртуальной машины (vm.args)»](../redundancy/redundancy.md#настройка-виртуальной-машины-vmargs).

База помнит имена своих узлов. Если имя в `vm.args` отличается от прежнего, узел не запускается: он ждёт узел с прежним именем. В `console.log` повторяются строки `trying to connect to 'fp@<прежнее имя>' node` и `'fp@<прежнее имя>' node is not available`, Studio не открывается. Остановите узел, исправьте `-name` и запустите его снова.

### 9. Запустить

Задайте предел открытых файлов, см. [«Запуск и остановка узла», раздел «Предел открытых файлов»](../start_stop/start_stop.md#предел-открытых-файлов).

Запустите узел как обычно, см. [«Запуск и остановка узла», раздел «Запуск в окне»](../start_stop/start_stop.md#запуск-в-окне). Узел присоединяется к работающим узлам кластера.

В [журнале сервера](../logs/logs.md) первого обновлённого узла должна появиться строка `upgrade faceplate version from <прежняя> to <новая>`: узел перевёл базу кластера на новую версию. У следующих узлов база уже переведена, в журнале строка `faceplate version <новая>`.

### 10. Мониторить

Проверьте:

- в [журнале сервера](../logs/logs.md) до запуска Runtime нет строк `error` и `crash`. Допустимы только строки `the attempt to obtain license failed` и `invalid license`: у узла нет лицензии, см. [«Лицензирование», раздел «Узел без лицензии»](../license/license.md#узел-без-лицензии);
- Studio и Runtime открываются по адресу этого узла, дерево проекта на месте, **О приложении** показывает новую версию;
- на панели **Сервера** работают все узлы кластера.

Если проверка не прошла, дальше не обновляйте. Остановите узел, верните его каталог установки из `faceplate_backup` и запустите узел как обычно: он присоединится к кластеру в прежней версии и получит от работающих узлов данные, записанные за время обновления. Сделайте архив с журналами и базой на момент запуска новой версии и передайте его в службу поддержки.

Сколько мониторить, зависит от объёма проекта.

### 11. Обновить

Обновите следующий узел так же, как первый:

1. Остановите узел — шаг [4](#4-остановить).
2. Сохраните его каталог установки — шаг [5](#5-сохранить).
3. Проверьте сетевые настройки — шаг [6](#6-проверить).
4. Распакуйте дистрибутив — шаг [7](#7-копировать).
5. Перенесите настройки в `vm.args` — шаг [8](#8-изменить).
6. Запустите узел — шаг [9](#9-запустить).
7. Проверьте узел — шаг [10](#10-мониторить).

Повторите для каждого узла, который ещё не обновлён.

# Заключение

Узлы обновляют по одному: узел останавливают, копируют его каталог установки вместе с базой и журналами в резервную папку, распаковывают новую версию поверх самого каталога установки и возвращают в `vm.args` прежние имя узла, cookie и `+MIscs`. Узел запускают как обычно, и он присоединяется к работающим узлам. Первый обновлённый узел переводит базу кластера, в журнале строка `upgrade faceplate version from … to …`. Затем проверяют журнал, Studio, Runtime и панель **Сервера** и обновляют следующий узел. Пока обновляется один узел, Runtime работает на остальных. При ошибках узлу возвращают сохранённый каталог, и он работает в кластере в прежней версии.
