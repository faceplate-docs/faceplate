# Назначение и роль в системе

Historian Server \- это специализированный высокопроизводительный узел программного комплекса FACEPLATE, предназначенный для накопления, долговременного хранения и оперативного извлечения больших массивов технологических данных (временных рядов и логов событий).

Использование выделенного Historian-сервера позволяет реализовать концепцию разделения данных:

* Runtime-данные: обработка оперативной информации «в памяти» для мгновенного управления.  
* History-данные: глубокое архивное хранение на дисковых носителях для последующего анализа, построения трендов и отчетов.

# Архитектура

В основе подсистемы хранения лежит СУБД Ecomet \- пообъектная база данных.

## Модель хранения

* Метаданные (RocksDB): высоконадежное хранение конфигураций объектов, их атрибутов и связей. Обеспечивает графовую структуру проекта (дерево объектов).  
* Временные ряды (Timeseries Engine): проприетарный движок для записи потоковых данных с устройств. Оптимизирован для последовательной записи с высокой плотностью (тысячи изменений в секунду).  
* Гибридный доступ: использование RAM для мгновенного доступа к срезам данных (Snapshots) и диска для архивов.

# Механизмы оптимизации данных

## Шардирование (Sharding)

Данные в Historian разбиваются на временные сегменты \- шарды.

* Каждый шард представляет собой отдельный набор файлов за фиксированный интервал (например, 1 час или 1 день).  
* Это позволяет системе выполнять «холодное» резервное копирование простым копированием файлов завершенных шардов и мгновенно удалять устаревшие данные.

## Сжатие LZ4

Для минимизации нагрузки на дисковую подсистему применяется алгоритм сжатия LZ4. Он позволяет уменьшить объем хранимых данных в 5–10 раз практически без потери производительности процессора, что критично для систем с глубиной архива в несколько лет.

# Политика удержания данных (Retention Policy)

Управление жизненным циклом данных осуществляется через параметр max\_age (максимальный возраст).

* Автоматическая очистка: Система циклически проверяет даты завершения шардов. Если шард полностью выходит за рамки установленного max\_age, он безвозвратно удаляется.  
* Гибкость настроек: Периоды хранения могут быть настроены индивидуально для разных типов данных (например, технологические параметры \- 1 год, системные логи \- 1 месяц).

# Распределенная работа и масштабируемость

Historian может функционировать в различных конфигурациях:

* Локально: на одном сервере с Runtime.  
* Выделенный узел: на отдельном сервере для распределения нагрузки. Запуск осуществляется командой: env ATTACH\_TO=fp@runtime-node ./bin/fp\_historian console.  
* Репликация (Hot Standby): поддержка «горячего» резервирования, при котором данные записываются одновременно на основной и дублирующий сервера Historian.

# Регламент технического обслуживания

Для обеспечения стабильной работы и предотвращения деградации производительности СУБД Ecomet, необходимо соблюдение следующих правил:

## Системные требования и лимиты

* Лимиты дескрипторов: Параметр ulimit \-n должен быть установлен в значение не менее 200,000. Недостаток лимитов приведет к аварийной остановке сервера при попытке открыть новые шарды.  
* Дисковое пространство: Обязательно наличие не менее 20% свободного места от общего объема диска. Это необходимо для фоновых процессов уплотнения (compaction) RocksDB. При заполнении диска на 80% работа системы считается критической.  
* Тип накопителей: Для систем с интенсивной записью (High Load) требуются Enterprise SSD/NVMe с высоким ресурсом перезаписи (DWPD).

## Мониторинг и безопасность

* Аудит: Регулярная проверка очередей записи и размера базы через интерфейс Studio (http://\<ip\>:8000/static/admin.html).  
* Электропитание: Обязательное использование ИБП с настроенным скриптом корректного выключения (shutdown) при низком заряде батареи для сохранения целостности индексов RocksDB.  
* Сетевая связность: При выносе Historian на отдельный узел рекомендуется использование выделенного сетевого интерфейса (VLAN) для защиты технологического трафика от задержек.
